# 전투 로컬 로그 및 Google Sheets 자동 전송

#### 2026-10-19 업로드 중복 확인 인덱스와 지연 진단 개선

- 진단: 기존 `doPost`는 업로드마다 Events의 전체 이벤트 키를 읽었다. 약 56,000행이 누적된 운영 시트에서 Apps Script 실행에 30초를 넘는 사례가 있었고, Unity의 30초 제한과 충돌해 `Request timeout`이 기록됐다. 업로드 거부·ACK 실패 뒤 종료된 기록은 로컬에 남아 후속 실행에서 재전송된다. `received_kst`와 `occurred_at_kst`의 차이를 Sessions 누락으로 해석하지 않는다. Sessions의 `started_kst`는 구간 시작 시각이다.
- 변경: 숨김 시트 `_TelemetryUploadIndex`에 세션별로 실제 저장된 사건 순번 구간과 Events checkpoint를 보관한다. 기존 Events는 최초 준비 때만 전체 확인하고, 운영 요청에서는 checkpoint 이후 행만 추가로 읽는다. 세션별 인덱스는 한 행씩 저장한다. 순번에 빈 구간이 있어도 최대 순번 이하라는 이유만으로 미수신 사건을 버리지 않는다.
- 저장 순서: Events에 이미 저장된 키를 색인한 후 색인 행을 먼저 flush하고 checkpoint를 쓴다. 현재 요청의 새 Events는 다음 요청에서 색인한다. 중간 실패로 Events만 저장돼도 다음 요청이 미색인 끝부분을 확인해 중복 추가를 막고, 기존 배치의 Sessions·OnboardingSteps 처리를 다시 시도한다. 최종 저장 확인 전에는 ACK하지 않는다.
- 처리량: 스테이지 요약이 없는 배치에서는 Sessions 읽기를 생략하고, 변경된 연속 행은 한 번에 쓴다. `received_kst`를 요청 처리 시작 시점에 기록한다. 실패 응답은 `busy`·`header_mismatch`·인덱스 오류를 구분하고 Apps Script 실행 로그에 실패 단계와 예외를 남긴다. 본문과 토큰은 로그에 남기지 않는다.
- 최초 적용: 로컬 Code.gs를 기존 Apps Script에 반영·저장하고 `prepareTelemetryUploadIndex`를 실행한다. `complete:true` 뒤 기존 웹 앱을 새 버전으로 배포한다. 준비는 최대 약 4분씩 이어서 실행할 수 있다. 원본과 URL·토큰·0.3.0/0.4.0 규약을 유지하므로 기존 게임 빌드에 적용된다. Unity 재빌드는 필요 없다.
- 운영: `rebuildTelemetryUploadIndex`는 파생 인덱스만 다시 만든다. 원본 수동 정렬·수정 뒤에는 재생성이 필요하다. 데이터 초기화 메뉴는 원본 세 탭과 파생 인덱스를 함께 비운다. 로컬 미전송 기록은 삭제하지 않는다. 인덱스는 대시보드·CSV 전송 대상이 아니다.
- 확인 범위: JavaScript 구문 확인 통과. 중복 배치·순서가 바뀐 순번·중간 저장 실패·초기화 후 재수신 경로를 코드 검토했다. 테스트 코드는 작성하지 않았다. 운영 저장·최초 인덱싱·새 버전 배포 및 배포 후 지연 개선 실측은 미확인이다. 적용 절차와 오류별 조치는 README에 기록했다.

#### 2026-10-19 Events는 기록되지만 Sessions가 누락되는 문제

- 원인: 기존 Sessions 탭의 헤더 순서는 예전 요약 열 배치(`retry_count`가 CL열)였다. 현재 Apps Script는 열 순서가 완전히 같아야 저장을 허용해 `header_mismatch`를 냈다. `doPost`는 Events를 먼저 저장·flush한 다음 Sessions를 갱신하므로 Events만 보이고 Sessions는 누락될 수 있었다. 서버 오류는 클라이언트에 `rejected_or_retry`로만 전달되어 로컬 JSONL이 ACK되지 않고 남는다.
- 수정: Sessions 기존 열은 이동하지 않고 헤더 이름을 기준으로 값을 매핑한다. 기존 헤더가 현재 지원하는 필드의 유효한 일부이면 빠진 헤더를 오른쪽에 추가한다. 알 수 없는 헤더나 중복 헤더는 데이터 오배치를 막기 위해 계속 거부한다.
- 배포: Apps Script 웹 앱 버전 11을 기존 URL에 배포했다. 실행 계정·액세스 범위와 UPLOAD_TOKEN은 변경하지 않았다.
- 검증: 로컬 로그에는 `stage_started`·`stage_summary`·`stage_ended`가 있는 0.1.3/스키마 0.4.0 JSONL이 남아 있었다. 기존 시트 행은 변경하지 않았다. v11 배포 후 실행 중이던 빌드가 업로드 ACK를 받았고 Sessions가 533개에서 536개 행으로 늘었다. 새 행에서 build `0.1.3`, stage `2-1`·`1-1`·`1-2`를 확인했다.

#### 2026-10-16 종료 시 네트워크 대기 제거

- 빌드 종료 요청은 `Application.wantsToQuit`에서 마지막 전투·온보딩 기록을 닫고, Google Sheets ACK를 기다리지 않고 즉시 허용한다. 기존 종료 전 최대 20초 업로드 유예를 제거했다.
- `OnDestroy`는 진행 중인 JSONL 저장 뒤 메모리 버퍼에 남은 마지막 사건을 로컬 JSONL에 추가하고 최대 1.5초 기다린다. ACK를 받지 못한 파일은 기존처럼 보존하며 다음 실행 때 재전송한다. 종료 과정에서 진행 중인 네트워크 요청은 중단된다.
- 로컬 저장이 1.5초 안에 끝나지 않으면 진단 경고를 남기고 종료를 계속한다. 디스크 쓰기가 제한 시간보다 오래 걸리는 환경에서 마지막 버퍼까지 보존됐는지는 미확인이다. 일반 플레이 중 자동 전송과 ACK 뒤 파일 정리 동작은 바꾸지 않았다.
- 구현 상태: `dotnet build Assembly-CSharp.csproj --no-restore` 성공(오류 0건, 기존 경고 2건). Unity Player 빌드 및 종료 실기는 미검증이다. 테스트 코드는 작성하지 않았다.

#### 2026-10-16 전송 완료 로그 즉시 정리

- 사용자가 전송 완료 로그의 즉시 삭제를 승인했다. TelemetryDiskStore는 AppendAsync에서 작성 중인 세션을 추적하고 `session_ended`가 디스크에 저장되면 비활성으로 전환한다. 온보딩도 최종 종료 때 기존 허용 이벤트 `session_ended`를 한 번 기록한다. 단계 종료만으로 세션을 닫지는 않는다.
- AcknowledgeAsync는 검증된 ACK 커서를 먼저 저장한 뒤 비활성 세션의 커서가 현재 JSONL 전체 길이와 정확히 같을 때만 JSONL·메타데이터 JSON·해당 세션 커서를 삭제한다. 삭제한 현재 스키마 원본 용량은 저장 예산에서 차감한다. 미전송·부분 전송·작성 중인 파일은 보존한다.
- ReadBatchAsync는 이전 실행에서 남은 완전 ACK 파일도 같은 목적지 커서를 확인하여 정리한다. 구버전도 완전 ACK가 확인된 경우에만 삭제한다. 강제 종료로 남은 미확인 원본은 보존하며 새 실행에서 현재 스키마 기록의 재전송을 이어간다.
- 스프레드시트 데이터·공유 토큰·익명 ID는 삭제하지 않는다. 로컬 원본은 전송 확인 후 사라지므로 장기 분석·백업은 스프레드시트에서 한다. C# 컴파일 오류 0건, 기존 경고 2건. 실제 플레이 중 전송·삭제 순서의 실기 확인은 미확인이다.

### 기능 이름

- 기능 설명: 온보딩, 1막, 2막의 도전별 진행과 플레이어 입력·피격·적 공격 결과를 기록한다. 현재 새 로그 스키마는 **0.4.0**, 게임 공통 계약 API는 **0.2.0**이며 기존 **0.3.0** 행도 수신·분석 호환된다.
- 동작 조건 및 처리 흐름: Recorder는 현재 Stage Controller의 구간을 시작 시점에 읽고 이후 전환 신호를 구독한다. `CombatTelemetryRunContext`가 씬 간 runId와 entryMode를 유지한다. 적 생명주기, Beast 도약, Twin Boss 부모 패턴과 개별 공격은 같은 AttackId·부모 패턴 ID로 연결한다. KatanaDamageReceiver가 확정한 접촉 결과가 판정의 권위 있는 결과다. 저장·재시도·ACK 커서 흐름은 유지한다.
- 구현 상태: S0–S7 코드·CSV·사이트 반영 완료. Apps Script 웹 앱 v11이 기존 URL에서 실행되고, v10 확인 시점에는 Events 51,405행·Sessions 533행·OnboardingSteps 335행이었다. `dotnet build Assembly-CSharp.csproj --no-restore` 성공(경고 0, 오류 0). Windows `StandaloneWindows64` Player 빌드가 성공했고 포함된 어셈블리에서 빌드 0.1.3 분석 설정과 스키마 0.4.0을 확인했다(BuildReport 오류 0건·경고 27건). Unity Editor 재컴파일 후 로컬 JSONL에서 0.1.3·0.4.0·구간 2-1·`stage_config`를 확인했다. v11 수정 후 Player 업로드 ACK 및 build `0.1.3` stage `2-1`·`1-1`·`1-2` Sessions 행을 확인했다. 2-2 공격 결과의 완전한 Sheets 적재 여부와 0.3.0·`unassigned` 보관 로그의 ACK는 미확인이다.

#### 연결 및 협업

- 연결된 기능: 전투 입력·방어 판정, 일반 적 패턴, 보스 패턴, Stage1 진행, 자동 업로드.
- 공유하는 상태: 세션 ID·AttackId 발급은 CombatSessionRuntime, 전투 판정은 KatanaDamageReceiver, 스테이지 전환은 Stage1Controller, 분석 누적은 Recorder가 관리한다.
- 중복 또는 충돌 사항: 기존 InputResolved 생산자를 사용하고 별도 키보드 폴링을 추가하지 않는다. ID와 관측 신호를 추가하며 전투 피해 수치는 변경하지 않는다.
- 수리검 패턴명은 `DefenseShuriken`으로 통일한다. BambooThrower는 전조 시작 시 이 이름으로 Begin을 한 번 보내고 같은 AttackId를 투사체에 전달한다. 투사체 Launch는 전달된 ID를 재사용해 Commit만 보내며, 접촉 결과도 같은 패턴명으로 기록한다. 시작 신호를 제거하면 전조 시각이 발사 시각으로 늦춰져 반응 시간이 왜곡되므로 Begin은 유지한다.
- `TryThrowForOnboarding` 경로는 BambooThrower의 자동 발사 전조 루프를 거치지 않으므로 투사체 Launch가 `DefenseShuriken` 시작 신호를 직접 발급한다. 두 경로 모두 세션 집계에서는 같은 패턴으로 합산한다. 전조 도중 취소된 공격은 시작·취소 사건은 남지만 Commit이 없으므로 실제 발사 시도 수에는 포함하지 않는다.
- 기존 `BambooShuriken` 로그는 변경 전 데이터로 보존한다. 변경 이후 새 로그에는 이 패턴명이 생성되지 않는다.
- 승인 필요 사항 및 결과: 사용자가 전조→입력과 입력→접촉을 모두 선택했고 기존 로컬 로그와 Google Events·Sessions 삭제를 승인했다. 엔드포인트·공유 토큰·익명 PC ID는 유지한다.

#### 집계 규칙

- 1-1은 웨이브와 보스 경고, 1-2는 보스 활성화부터 사망/완료까지다. 보스 재도전은 1-1 행을 생성하지 않는다. Sessions의 키는 `sessionId:stageId`이며 구간마다 1행이다. 재전송은 최신 누적 값으로 덮어써 이중 합산하지 않는다.
- `deaths`는 도전당 0 또는 1. `activePlaySeconds`는 Playing 동안 실제 경과 시간으로 일시정지·게임오버 대기를 제외한다. 경고/등장 연출도 Playing이면 포함한다. 강제 종료는 최신 `in_progress` 요약만 남을 수 있다.
- `player_input.isAttempt=true`인 고유 InputId만 시도 수에 포함한다. Rejected도 시도다. GuardHoldResume·GuardRelease는 새 시도가 아니다. Buffered→Started는 1회다. 실제 회피 시작은 dodgeStarted로 별도 집계한다.

#### 2026-10-16 HBB 진단: 구버전 로그로 인한 저장 한도 소진

- 제공된 HBB 진단 폴더의 Player.log 37행에서 로컬 저장 한도 초과를 확인했다. JSONL 36개가 모두 스키마 0.2.0이며 합계 104,857,506바이트로 100MiB 한도에 94바이트만 남아 있었다. 현재 버전 사건은 한 건도 저장되지 않았다.
