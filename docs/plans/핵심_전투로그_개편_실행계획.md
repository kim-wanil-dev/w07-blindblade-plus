# 핵심 전투 로그 개편 실행 계획

- 작성: 2026-10-21.
- 상태: S0–S5 구현과 검증 완료. S6의 Unity Editor Play는 부분 검증했고 Sites 버전 23을 기존 공개 URL에 배포했다. Apps Script 운영 배포와 실제 ACK는 미확인이다.
- 실행 모델: Unity·Apps Script·CSV는 Luna max, Sites 대시보드 통합은 Sol high를 사용했다.
- 작업 브랜치 확인: 작업 브랜치는 `feature/log`다. 사용자가 이번 개편 관련 파일에 한해 Git 조회·스테이징·커밋·푸시를 명시적으로 허용했다. 게임 저장소 커밋 `d8497f16`을 해당 브랜치에 푸시했다.
- 범위: Unity 기록 생산자 → 로컬 저장/전송 → Apps Script → CSV → Sites 전체요약. 나머지 페이지는 legacy로 보존한다.

## 1. 사용자와 확정한 기준

1. 분석 세션은 구간별 한 번의 도전이다. 1-1, 1-2, 2-1, 2-2를 각각 나누고 재도전도 반드시 새 세션이다.
2. 방어는 고유 입력당 대표 결과 하나만 집계한다. 퍼펙트 패링 > 일반 방어 > 성공 없음 순이다.
3. 세션 이탈은 구간 완료 전 종료이며 사망 후 종료도 포함한다. 재도전은 이탈이 아니다. 강제 종료 등 확정할 수 없는 기록은 종료 미확인으로 구분한다.
4. 플레이어 이탈은 세션 이탈률의 평균이 아니다. 전체 고유 플레이어 중 최종 게임 클리어 전에 종료한 플레이어 비율과 종료 구간을 본다.
5. 피격 순간 인지 반경 안의 일반 적, 보스, 적대 수리검과 합계를 기록한다. 화면 노출, 시선 방향, 은폐 여부로 제외하지 않는다.
6. 핵심 지표 7종은 모두 전체요약 안에서 열람한다. 다른 페이지는 수정하지 않는다.
7. 나머지 로그는 유지한다. 핵심 기록 손실·중복·자원 경합을 일으키는 수집 경로만 근거를 남겨 축소 또는 제거한다.

## 2. 코드에서 확인한 현황과 미확인 사항

| 확인 위치 | 확인 결과 | 계획에 반영할 사항 |
| --- | --- | --- |
| `CombatSessionRuntime.Initialize` | 새 GUID와 런타임 세대를 생성한다 | 재도전 ID 누락을 단정하지 말고 실제 초기화·기록자 연결을 확인 |
| `GameSceneInitializer.Initialize` | 전투 런타임을 초기화한다 | 재도전 씬의 실제 호출 및 새 기록자 생성 확인 |
| `CombatTelemetryRecorder.BeginStage` / `Record` | 구간마다 카운터 초기화, 기존 stageAttemptId는 sessionId:stageId | 구간 도전을 명시적으로 식별하고 같은 구간 재진입도 충돌 방지 |
| `HandleDeath` / `LateUpdate` / `Close` | Died에서 deaths=1, 프레임 말에 최종 구간 요약, 비활성화·앱 종료 때 세션 닫기 | 사망 콜백 순서·구간 선종료·저장·요약 덮어쓰기를 추적. 원인은 미확인 |
| `HandleInput` / `ResolveAttack` | 입력은 InputId로 중복 제거하지만 방어 결과는 접촉 수 | 입력별 대표 결과 집계 추가 |
| `HandleInput` | 중복 입력 기록이면 Started 처리 이전에 반환하는 경로가 있다 | Buffered→Started의 입력 연결 누락 가능성 확인 |
| `HandleDodge` | Started·PerfectDodge 사건은 기록, 요약에는 dodgeStarted 반영 | 고유 DodgeId 기준 극한 회피 횟수 추가 |
| `CombatTelemetrySignals` | 일반 회피와 극한 회피가 모두 outcome=Dodge로 기록될 수 있다 | 공격별 방어 판정과 회피 무적의 원인을 명시적으로 분리 |
| `PlayerEmpower` / `PlayerSwordWaveLauncher` | 일섬의 실제 검기 발사와 거합 시작 경로, 자동 반격 경로가 존재 | 입력 시도와 실제 발동 분리, 수동 거합과 자동 반격 구분 |
| `Code.gs` | 원본 Sessions에는 anonymous_player_id가 있으나 대시보드 허용 열에는 없다 | 자동 조회에도 플레이어 ID 전달 |
| `renderOverview` / `renderPlayerTotals` | 현재 전체요약은 구간 집계 중심, 플레이어 시간 표 존재 | 핵심 세션 표·플레이어 이탈 표로 교체/확장 |
| `SensoryManager` | `_maximumDistance`와 거리 기반 인지 감쇠가 존재 | 실제 설정을 반경 원천으로 사용; 렌더러 표시 여부와 분리 |

- 생산자 스키마는 0.5.0으로 갱신했다. 0.3.0·0.4.0 로그 호환성은 유지한다.
- S0의 제공 로컬 표본에서는 재도전-사망-이탈 순서를 재현하지 못했다. 운영 Sites 소스와의 일치는 확인했고, 실제 Apps Script 시트 적재는 미확인이다.
- 이전 계획의 Unity 생산자 수정 제외 조건은 이번 사용자 요청으로 범위가 확장되었다. 과거 검증 기록은 덮어쓰지 않는다.

## 3. 식별자와 세션 수명

### 3.1 분석 세션과 전투 런타임

- 전투 런타임의 sessionId·공격 ID·시간 기준은 구간 전환만으로 초기화하지 않는다. 전투 동작과 진행 중 공격의 상관관계를 보존한다.
- 신규 `attemptSessionId`를 구간 진입마다 발급한다. 핵심 화면에서 말하는 세션 ID는 이 값이다. 신규 스키마의 stageAttemptId도 같은 도전 키를 사용한다.
- 기존 `sessionId`는 런타임 식별자로 남기고 `runId`, `anonymousPlayerId`, stageId, retryIndex, previousAttemptSessionId, entryMode를 함께 기록한다.
- 입력·공격의 중복 제거에는 도전 키만 사용하지 않는다. 원본 ID가 할당된 런타임 sessionId와 InputId/AttackId/DodgeId를 조합한다.
- 구간 경계를 넘는 공격은 시작 구간을 소유자로 고정한다. 경계에서 이전 공격을 Interrupted로 닫으면 이후 도착한 동일 공격 결과를 새 구간에 다시 넣지 않는다. 이 정책은 실제 게임 공격을 취소하는 명령이 아니다.
- 방어를 누른 채 구간이 바뀐 경우 GuardHoldResume를 새 누름으로 세지 않는다. 이전 입력에 속한 접촉의 귀속과 새 구간의 입력 연결 없음 상태를 구분한다.
- 온보딩도 현재의 5개 구간 도전을 같은 분석 키 규칙으로 식별한다. 정식 전투를 기본 필터로 하고 온보딩 포함을 선택할 수 있게 한다.

### 3.2 사망·재도전·종료

1. 사망 순간 player_died를 한 번만 기록하고 해당 도전 deaths=1을 확정한다.
2. 같은 프레임의 치명타 최종 결과를 먼저 반영한 뒤 구간 요약을 death로 확정한다. 콜백 순서 때문에 치명타 결과를 버리지 않는다.
3. 재도전 버튼은 이전 도전 종료를 보장하고, 새 구간 시작에서 새 attemptSessionId를 만든다. 이전 카운터를 새 도전에 넘기지 않는다.
4. 일반전→보스전 전환에서는 이전 구간을 cleared로 닫고 새 구간 도전을 시작한다.
5. 확정된 death/cleared 요약은 뒤늦은 in_progress·OnDisable·중복 전송으로 되돌리지 않는다. 서비스 수신 시각 대신 사건 순번과 종료 상태를 기준으로 최신값을 선택한다.
6. 사망 뒤 앱을 종료하면 deaths=1을 유지하면서 별도 종료 사실을 마지막 도전에 연결한다. 사망 종료 사실과 앱 종료 사실은 둘 다 보존한다.
7. 구간 클리어 후 앱 종료는 해당 구간의 이탈이 아니다. 최종 게임 클리어 전이면 플레이어 기준 이탈에는 포함하며 `구간 완료 후/다음 구간 진입 전`으로 표시한다.
8. 최종 게임 클리어는 마지막 보스/게임 클리어의 명시적 사건으로 기록한다. 개별 stage cleared나 runId 변경을 최종 게임 클리어로 취급하지 않는다.
9. 강제 종료·디스크 저장 실패·전송 대기는 확정 이탈로 추정하지 않는다. 로컬 종료 마커와 다음 실행 복구를 지원하더라도 `복구된 비정상 종료`와 정상 종료를 구분한다.

## 4. 핵심 지표 계약

### 4.1 방어 입력

- 총 방어 입력 = 고유 GuardPress 시도. 실행 거부 입력도 시도에 포함한다. GuardRelease, HoldResume, Buffered→Started 재통지는 추가 입력이 아니다.
- 입력별 상태를 기록하고 같은 입력의 결과는 `성공 없음 → 일반 방어 → 퍼펙트 패링` 방향으로만 승격한다.
- 일반 방어 후 퍼펙트 패링이 나오면 일반 방어 입력 수에서 1을 빼고 퍼펙트 패링 입력 수에 1을 더한다.
- 성공 없음은 아직 접촉하지 않은 입력·거부·방어 실패 등을 포함한다. 진행 중 입력은 잠정값임을 표시하고, 거부 수는 보조 정보로 남긴다.
- `총 방어 입력 = 일반 방어 입력 + 퍼펙트 패링 입력 + 성공 없음 입력`이 항상 성립해야 한다.
- 구형 NormalParry를 일반 방어로 임의 합산하지 않는다. 새 게임에서도 발생하는지 추적하고 별도 의미가 남아 있으면 기타 판정으로 표시한다. 일반 방어는 요청대로 피해만 막은 Guard다.

### 4.2 회피 입력과 실제 회피

- 총 회피 입력 시도, 실행 거부, 실제 회피 시작을 구분한다. 주 지표 `회피 횟수`는 실제 시작한 고유 DodgeId 수다.
- 극한 회피 횟수 = PerfectDodge가 한 번 이상 발생한 고유 DodgeId 수. 한 회피로 여러 공격을 극한 회피해도 회피 성공 횟수는 1이다.
- 핵심 화면에는 총 입력·실행 회피·극한 회피를 표시하고, 실행 회피를 일반 회피/극한 회피 성공으로 나눈 막대를 사용한다.
- `극한 회피 횟수 ≤ 실제 회피 횟수 ≤ 총 회피 입력`을 기본 점검한다. 온보딩 강제 실행 등 입력 없는 시작은 출처를 별도로 기록한다.

### 4.3 적 공격 결과

- 적 공격 한 건은 고유 AttackId의 최종 결과 하나다. 부모 보스 패턴과 개별 타격을 중복 합산하지 않는다. 수리검은 투사체별 공격 ID를 사용한다.
- 전체 결과는 종료가 확정된 공격 수다. 시작만 하고 진행 중인 공격은 별도 대기 수이며 분모에 넣지 않는다.
- 표시 열: 전체 결과, 유효판정, 적중, 회피, 극한회피, 방어, 퍼펙트패링, 빗나감, 취소, 중단.
- 요청 목록 밖의 Invulnerable, Destroyed, Ignored, NormalParry 등이 실제로 존재하면 기타 열과 원인별 상세를 추가한다. 이를 요청된 결과로 억지 변환하거나 숨기지 않는다.
- 유효판정은 실제 실행된 공격의 Hit/일반 회피/극한 회피/Guard/PerfectParry/Miss/NormalParry다. 취소·중단·무관한 무적·파괴·판정 제외는 제외하며, 이유별 수는 전체 결과에 남긴다.
- 전체 결과 = 모든 상호 배타적 최종 결과의 합. 유효판정 적중률 = 적중 합 / 유효판정 합. 분모 0은 `—`다.
- 일반 회피 무적과 스킬 무적이 둘 다 Invulnerable로 나올 수 있으므로 방어 생산 시점에 원인을 구분한다. 회피 중이라는 이유만으로 다른 무적을 회피로 바꾸지 않는다.
- 공격별 극한 회피는 해당 접촉의 `defenseOutcome=DodgeAvoided`로 분류한다. 일반 회피 무적은 `Dodge`, 다른 무적은 `Invulnerable`로 남기며, 먼저 도착한 접촉을 나중 DodgeId 보상 사건으로 재분류하지 않는다.
- 입력 기준의 극한 회피 횟수와 공격 기준의 극한회피 결과 수는 서로 다를 수 있다. 화면 설명에 단위를 명시한다.

### 4.4 피격 순간의 주변 적대 개체

- 적중 판정 및 실제 적용 피해가 양수인 사건마다 피해 처리 직전의 위치·활성 개체 목록을 스냅샷으로 얻고, 피해 확정 결과에 함께 저장한다. 같은 프레임 사망·수리검 제거보다 앞선 목록을 사용한다.
- 반경은 SensoryManager의 실제 최대 인지 거리 설정을 원천으로 한다. 실행 시 참조 경로와 프리팹 저장값을 확인해 중복 설정값이나 임의의 고정 숫자를 만들지 않는다.
- 거리 판정은 해당 인지 시스템과 같은 3D 월드 거리, 반경 경계 포함이다. 카메라 시야·가림·현재 공개 여부는 검사하지 않는다.
- 살아 있는 일반 몬스터, 살아 있는 보스, 활성 적대 투사체를 개체별 한 번씩 센다. 적대 투사체는 `DefenseShuriken`, `EnemyProjectile`, `TwinBossProjectile`을 포함하고 GameObject 기준 중복을 제거한다. 반사된 아군 투사체·비행 종료 또는 파괴된 투사체·사망 적·장식은 제외한다.
- 반경 안에 있는 공격자와 피격을 일으킨 수리검도 포함한다. 보스가 둘이면 2개체다.
- 필드: snapshot 시각, 플레이어 위치, 사용한 반경, normalEnemyCount, bossCount, hostileShurikenCount, hostileTotalCount, snapshot 수집 상태.
- `합계 = 일반 적 + 보스 + 수리검`. 표본 누락은 0개와 구별한다.
- 활성 개체 레지스트리 또는 기존 목록을 이용해 피격 시에만 수집한다. 매 프레임 전체 씬 검색은 하지 않는다. Physics 버퍼 사용 시 포화 감지 없이 일부만 세는 구현은 금지한다.
- 화면에는 피격별 상세표와 개체 수별 피격 건수 분포를 제공한다. 체류 시간 분모가 없으므로 이를 개체 수별 피격 확률로 표시하지 않는다.

### 4.5 일섬·거합

- 실제 발동된 스킬 실행 ID별 1회. 버튼 누름, 예약, 차징 시작, 취소, 적 피격 수로 세지 않는다.
- 일섬: PlayerSwordWaveLauncher의 실제 Launch/SwordWaveLaunched 경로 기준. 예약 단계 Arm에서 세지 않는다.
- 수동 거합: PlayerEmpower.TryBeginStrike의 성공 및 실제 시작 기준. `skillSource=manual`만 사용량에 합산하고 같은 실행의 Started·Play·완료 사건은 중복 합산하지 않는다.
- BeginCounterStrike 자동 반격은 `player_skill_activated` 사건에 `skillSource=counter`로 보존하되 수동 거합 사용량에서 제외한다. 온보딩 강제 발동도 source를 구분한다.
- UI 용어는 일섬·거합을 사용하고 코드 내부 명칭과 연결표를 문서화한다.

### 4.6 세션별 사망·이탈·시간

- 세션 상세: deaths(0 또는 1), 종료 상태, 이탈 여부, 활성 플레이시간, 시작/종료 시각.
- 활성 시간은 Playing 상태의 실제 경과 시간이다. 일시정지·게임오버·로딩 대기를 제외하고, 슬로모션 배율로 실제 시간을 줄이지 않는다.
- 세션 이탈률 = 이탈이 확정된 도전 수 / 종료가 확정된 도전 수. 진행 중·종료 미확인은 분모에서 제외하고 건수를 함께 표시한다.
- 사망 후 재도전은 사망 도전이며 이탈 아님, 사망 후 앱 종료는 사망 도전이면서 이탈이다. 확인된 앱 종료가 없으면 이탈 여부는 미확인이다.
- 재전송된 누적 요약은 최신 한 행만 사용하며 Events와 Sessions를 같은 도전의 추가 횟수처럼 더하지 않는다.

### 4.7 플레이어별 시간과 전체 플레이어 이탈률

- 플레이어는 anonymousPlayerId로 중복 제거한다. 동일 PC의 여러 사람을 구분하지 못하는 현재 한계를 표기한다. ID 누락은 별도 건수이며 한 플레이어로 묶지 않는다.
- 플레이어별 총 플레이시간은 고유 도전의 최신 활성 시간 합이다. 시간 미수집을 0으로 채우지 않는다.
- 전체 플레이어 이탈률 = 첫 최종 게임 클리어 전 앱 종료가 확인된 고유 플레이어 수 / 분석 대상 고유 플레이어 수.
- 최초 클리어 이전에 한 번 종료했다가 나중에 복귀·클리어해도 과거 이탈 경험은 유지한다. 별도로 현재 상태(복귀 중/최종 클리어/종료/미확인)를 표시한다.
- 분모에는 분석 대상 전체 플레이어를 포함한다. 종료 미확인·진행 중 비중과 수집 범위를 함께 표시하여 확인된 이탈 비율임을 밝힌다. 미확인을 정상 완료로 분류하지 않는다.
- 대표 이탈 구간은 플레이어별 첫 클리어 전 최초 확인 종료 구간이다. 한 플레이어가 여러 곳에서 나가도 대표 구간 분포에는 1회만 포함한다. 모든 종료 이력은 상세에서 확인한다.
- 구간 전환 중 종료는 마지막 완료 구간과 다음 진입 예정 구간이 있으면 함께 표시한다. 이미 완료한 구간에서 전투 중 이탈한 것처럼 표시하지 않는다.
- 최종 완료 여부는 stage cleared가 아니라 명시적인 game_completed 사건으로 판단한다.
- 빌드·기간·Editor 필터로 플레이어 집단을 먼저 정하고, 이 집단의 첫 클리어/종료 순서는 조회 가능한 전체 이력으로 확인한다. 구간 필터는 이탈 위치 표시를 좁힐 뿐 전체 플레이어 분모를 몰래 바꾸지 않는다.
- 기간 이후 복귀·클리어는 별도 후속 상태다. 과거 기간의 종료 사실을 지우지 않는다. 과거 이력이 부족하면 최초 플레이/최초 클리어를 확정하지 않는다.

## 5. 저장·전송·조회 호환성

- 신규 의미를 명확히 구분하기 위해 0.5.0 스키마를 계획한다. 기존 0.3/0.4 원본과 legacy 열은 보존하고 새 계약을 별도 문서화한다.
- 새 도전 키, 입력 대표 결과, 회피 구분, 스킬 실행, 피격 스냅샷, 종료·최종 클리어, 핵심 요약을 생산자부터 API까지 일관되게 전달한다.
- Code.gs의 허용 이벤트·스키마·Events/Sessions 열·대시보드 읽기 허용 열·중복 키·요약 upsert를 함께 수정한다. 기존 열 위치를 바꾸지 않고 신규 열은 추가한다.
- Sessions에 핵심 카운터를 제공하여 전체요약 첫 화면이 모든 Events 다운로드 완료를 기다리지 않게 한다. 피격별 상세 등은 같은 스냅샷의 Events로 보완한다.
- 플레이어 종료/최종 클리어 집계가 다량 Events 전체 조회에 의존하지 않도록 core 응답에 종료 이력용 소규모 집계를 제공한다. 기존 도전의 death/cleared 상태를 앱 종료 이유로 덮어쓰지 않는다.
- CSV 변환기와 데이터 사전도 같은 단위·누락값·중복 제거 규칙을 사용한다. 자동 연결과 CSV 결과가 같아야 한다.
- 업로더가 버전 변경 뒤 이전 스키마의 미전송 파일을 무조건 건너뛰지 않도록 지원 버전·저장 용량 정책을 점검한다. 기존 디스크 로그, 전송 커서, 시트 행을 일괄 삭제하지 않는다.
- 구형 기록에서 정확히 복원할 수 있는 필드만 사용한다. 입력 대표 결과·극한 회피·피격 주변 개체 수를 추정해 채우지 않는다. 새 핵심 계약 데이터를 기본 비교 집단으로 삼고 과거 데이터는 수집 범위를 표시한다.
- R2 공유 캐시는 읽기 계약/캐시 버전을 구분해 새 필드가 빠진 구캐시를 재사용하지 않게 한다. 원본 시트 초기화로 캐시를 갱신하지 않는다.
- 조회 스냅샷의 Sessions 순번과 Events 상한을 맞추고, 부분 수신 시 마지막 완성 자료와 불완전 상태를 표시한다. 수신 중인 값과 완료된 값을 합치지 않는다.

## 7. 실행 순서와 완료 조건

### S0. 현상 재현과 계약 고정

- 실행 시작 시 AGENTS.md와 관련 명세, 사용자 변경 유무를 확인한다. feature/log에서는 Git CLI를 쓰지 않는다.
- 실제 최신 플레이 기록으로 사망→즉시 재도전→재사망→앱 종료를 추적한다. 로컬 player_died, stage_ended, session_ended, ACK, Sheets, 전체요약을 차례로 대조한다.
- 누락이 발생한 최초 경계와 실제 구간/세션 키를 기록한다. 재현이 안 되면 미재현으로 남기고 원인을 단정하지 않는다.
- 스키마/데이터 사전에 이 문서의 단위와 분모를 먼저 반영한다. 게임 판정 동작은 바꾸지 않는다.

### S1. 구간 도전·사망·종료 수명 수정

- CombatTelemetryRecorder, OnboardingTelemetryRecorder, 필요한 GameStateManager/구간 전환 연결을 수정한다.
- 새 도전 ID, 사망 정확히 1회, 최종 요약의 단조 갱신, 재도전 연결, 종료와 최종 클리어 사실을 구현한다.
- 완료 조건: 연속 재도전 시 각각 다른 분석 세션과 정확한 사망 1건, 이전 도전 수치 불변.

### S2. 방어·회피·적 공격 핵심 집계

- 입력별 대표 결과와 승격, 입력 거부, Buffered→Started 연결, 고유 DodgeId 성공 집계를 구현한다.
- 방어 생산자에서 일반 회피/극한 회피/스킬 무적을 구분해 공격 최종 결과까지 전달한다.
- 완료 조건: 입력 수 보존식, 공격 결과 합계, 회피 입력과 접촉 단위 구분을 실제 기록으로 확인.

### S3. 피격 스냅샷과 스킬 발동

- 활성 적·보스·수리검의 반경 스냅샷을 피격 확정에 연결한다. 풀 반환·반사·복수 Collider를 처리한다.
- 일섬 실제 발사와 수동 거합 성공 시작을 실행 단위로 기록하고 자동 반격을 분리한다.
- 완료 조건: 알고 있는 배치의 개체 수와 일치, 사망 타격의 수리검 포함, 다중 타격이어도 스킬은 1회.

### S4. 로컬·Apps Script·CSV·캐시

- 새 스키마를 저장/수신/전달하고 기존 기록을 지원한다. 중복 업로드와 역순 요약에서도 최종값을 보존한다.
- 플레이어 ID와 종료·최종 클리어 자료를 core 응답에 추가하고 캐시 버전을 갱신한다.
- 완료 조건: 같은 사건의 JSONL·CSV·Sheets·API 값 일치, 구형 행과 미전송 로그 보존.

### S5. 전체요약 개편

- core 전용 집계와 일관된 분모를 구현하고 위 화면 구성을 적용한다.
- 플레이어 수 기반 이탈률 및 최초 이탈 구간, 나중에 복귀·클리어한 상태를 표시한다.
- 완료 조건: 핵심 7종을 선택 구간 도전의 합계·통계로 전체요약 기본 화면에서 조회 가능, 도전별 상세는 선택적으로 열람, legacy 페이지 구성 유지, 누락을 0으로 표시하지 않음.

### S6. 수동 검증·배포·명세 갱신

- 테스트 코드는 작성하지 않는다. 기존 빌드/문법 검사와 실제 플레이·CSV 대조·브라우저 확인을 수행한다.
- 수신기의 신구 스키마 지원 → API/캐시와 전체요약 → 새 게임 빌드 순으로 반영해 구버전 클라이언트도 계속 수신되게 한다.
- Sites 운영 프로젝트는 기존 project_id와 공개 범위를 유지하고, 구현 시작 시 최신 소스를 확인한다. 저장소 사본과 운영 소스를 비교하지 않은 채 오래된 사본으로 덮어쓰지 않는다.
- Sites 소스 동기화 helper는 Sites 저장소의 `main` 브랜치에 커밋·푸시한다. 이번에는 사용자의 명시적 Git 허용 범위에 따라 helper로 원격 소스를 열고, 변경 소스를 빌드·패키징·배포한다. 게임 저장소 브랜치는 변경하지 않는다.
- 구현 시 Sites/Unity 작업에 해당 스킬을 읽는다. Apps Script 소유자 배포가 필요한 경우 로컬 코드 준비와 실제 배포 완료를 구분한다.
- 관련 기능명세·FEATURE_SPEC·README·데이터 사전을 갱신하고, 검증 증거/미확인/배포 버전을 기록한다. 실패·미배포를 완료로 표시하지 않는다.
