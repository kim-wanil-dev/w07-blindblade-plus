## 2. 확인된 문제와 수정 방향

### F01 · P0 · 온보딩 빌드 필터와 Editor 제외 오류 — 운영 표본 재현

- 위치: v12 `filtered`(479행), `renderOverview`(798행), `renderOnboarding`(939행), `onboardingStepRows`(855행).
- OnboardingSteps에는 `build_version`, `config_version`이 없다. 그런데 KPI와 목표 표는 `filtered(data.steps,'step')`에서 이 열을 직접 검사한다. 반면 마지막 진행 표는 Sessions에 연결하는 별도 함수를 사용한다.
- Editor 제외 기본값에서 목표는 **153건**이어야 하는데 KPI·목표 표는 **186건**을 사용한다. **33건**이 섞인다.
- 빌드 `0.2.0` 선택 시 올바른 연결로는 **64건**인데 직접 필터 경로는 **0건**이다. `0.1.3`은 11건, `0.1.4`는 46건, `0.2.1`은 32건을 표시할 수 있으나 같은 이유로 0건이 된다.

### F02 · P0 · Events 실패 시 피해 대체 집계의 중복 합산 — 운영 표본 재현

- 위치: `damageCauseRows`(833행), 생산자 `CombatTelemetryRecorder.Summary`.
- 생산자의 `rangedDamage`는 **모든 Projectile**, `meleeDamage`는 **그 밖의 모든 공격 종류**의 합이다. 일반 몬스터 전용 합이 아니다.
- 현재 사이트는 이를 ‘일반 원거리/근거리’로 표시한 뒤 `bossRangedDamage`, `bossEscapeBarrageDamage`, `bossChargeDamage`를 다시 더한다. 보스 피해가 중복되고 Beast·쌍둥이 구분도 사라진다.
- 기본 Editor 제외 표본: Sessions의 실제 `damageTaken` 합은 **9,449.826008**, 현재 대체 막대의 합은 **10,925.898130…**이다. 약 **15.6%** 과대 표시한다.
- 수정: 패턴별 대체 표시는 Sessions의 기존 `patterns_json`을 제한적으로 읽어 상호 배타적으로 합산하는 방법을 우선 검토한다. 그 열을 제공하지 못하면 `rangedDamage`와 `meleeDamage`만으로 ‘전체 원거리/기타 공격’이라는 거친 분류를 표시한다. 세부 보스 합을 추가로 더하지 않는다.
- ‘피해량 비중’은 실제 피해 합으로 나누어 %를 표시한다. 현재 막대 길이는 최대 항목 대비이며, 값도 피해량이다. 최대 대비 길이를 전체 피해 비율로 읽게 해서는 안 된다. 피격 횟수 비중과 피해량 비중도 분리한다.

### F03 · P0 · 부분 Events와 최신 Sessions를 하나의 표본처럼 사용 — 운영·코드 확인

- 위치: `connectSheet`(380행), `renderCombat`, `damageCauseRows`, `renderEnemyComposition`, Apps Script `dashboardSnapshot`·`dashboardRowsPage`.

- 신규 조회 중 CSV 가져오기·초기화·다른 조회가 발생하면 이전 비동기 응답이 덮어쓰지 못하도록 요청 세대 ID와 취소 처리를 적용한다.

### F04 · P1 · 쌍둥이 개별 공격 표의 판정 분모와 숨겨진 결과 — 운영 표본 재현

- 위치: `renderCombat`(961행), `renderTwinAttackOutcomes`(996행), 생산자 `ResolveAttack`(372행).
- 생산자는 Commit 전 취소도 종료 사건으로 남긴다. 그런데 개별 표는 시도는 Commit 수로, 판정은 취소·중단을 포함한 모든 resolved 수로 계산한다.
- 기본 Editor 제외 수리검: **시도 517 / 판정 550**, 이 중 `Cancelled` 40건이다. 실제 실행 후 취소·중단을 뺀 판정은 **510**, Hit은 81이다. 현재 개별 표의 적중률은 `81/550=14.7%`, 생산자·일반 표와 맞춘 비율은 `81/510=15.9%`다.
- 짐승 물기도 **시도 203 / 모든 종료 235 / 유효 판정 183**으로 같은 문제가 있다. ‘모든 종료’ 수가 시도보다 많은 것은 사건 구조상 가능하지만 이를 같은 의미의 판정 분모로 표시하면 안 된다.
- 일반 표도 `Destroyed`, `Invulnerable` 등을 분모에는 넣지만 열에는 표시하지 않는다. 기본 표본에 Destroyed 22건·Invulnerable 23건이 있어 표시된 결과 합과 판정 합이 맞지 않는다.
- 수정: 하나의 공격 정규화 결과에서 두 표를 만든다. 전조 시작, 실행, 실행 전 취소, 실행 후 취소·중단, 유효 판정, 진행 중을 구분한다. 유효 판정의 모든 결과를 열 또는 ‘기타 결과’ 상세로 설명한다. 기존 생산자의 적중률 정의를 유지하고 다른 분모의 비율은 별도 이름을 붙인다.
- Commit 누락이 의심되는 과거 결과를 조용히 삭제해서 합을 맞추지 않는다. 해당 도전의 표본 불완전으로 표시한다.

### F05 · P1 · 부모 패턴을 한 종류로 오표시하고 CSV 집계를 덮어씀 — 운영·코드 확인

- 위치: `renderTwinAttackOutcomes`.
- 현재 그룹 키는 `pattern_id` 하나인데 부모 패턴 열은 처음 발견한 값 하나를 표시한다. 실제 `TwinBeastBite`는 **IaiCharge와 AlternatingMelee** 양쪽에서 기록됐다. 표는 한쪽만 대표로 표시한다.

### F06 · P1 · 최신 빌드 비교 누락과 전역 필터 예외 — 운영·코드 확인

- 위치: `renderBuildComparison`(529행), `renderEnemyComposition`(662행), `renderStageFunnel`(546행), `updateBuilds`(496행).
- 비교 표는 제목·대상 빌드가 `0.1.2 / 0.1.3`으로 고정이다. 실제 6개 빌드 중 `0.1.2`는 이번 표본에 없고 `0.2.0~0.2.2`가 있다.
- 비교 표는 구간·빌드 선택을 모두 무시하고, 2-1 적 구성 카드는 구간 선택을 무시한다. **1-2만 선택해도 2-1 구성 표가 표시되는 것**을 재현했다.
- 빌드 선택지는 Sessions에서만 만든다. Events만 가져온 CSV는 빌드 정보가 있어도 선택할 수 없다.
- 수정: 빌드 선택지는 근거가 있는 자료의 메타데이터 합집합으로 만들고 버전 순서로 정렬한다. 비교 표는 선택 빌드·구간을 따른다. 2-1이 선택 범위 밖이면 해당 구성 카드는 범위 밖으로 표시한다. 퍼널처럼 전체 진행을 봐야 하는 카드는 ‘선택한 실행의 전체 진행’이라는 코호트 규칙을 별도로 명시한다.

### F07 · P1 · 온보딩 입력 결과를 수집하고도 사이트에서 확인할 수 없음 — 코드 확인

- 위치: `DASHBOARD_STEP_HEADERS`, `DASHBOARD_EVENT_HEADERS`, `renderOnboarding`.
- 시트의 OnboardingSteps에는 `started_inputs`, `rejected_inputs`, `buffered_inputs`, `dropped_inputs`가 있다. 현재 읽기 API와 목표 표는 이 값을 제외한다.
- 개별 `onboarding_attempt`의 `input_status`, `expected`, `defense_outcome`, `input_id`도 분석용 응답에서 빠져 있어 ‘시도했는데 거부됐는지’, ‘요구 입력이었는지’, ‘방어 접촉이 성공했는지’를 연결하기 어렵다.
- 수정: 이미 저장된 해당 열만 읽기 허용 목록에 추가하고, 목표별 입력 결과와 필요할 때 입력 상세를 표시한다. 목표 완료율, 입력 실행률, 방어 접촉 성공은 각각 단위가 다르므로 하나의 성공률로 합치지 않는다. 기존 입력 결과를 받는 작업은 Unity 재빌드가 필요 없다.

### F08 · P1 · 최근 온보딩 위치와 최대 도달 위치, 날짜 기준이 혼재 — 코드 확인

- 위치: `onboardingProgressSessions`(879행), `filtered`, `onboardingStepRows`.
- ‘마지막 단계’는 최근 발생 순서가 아니라 가장 큰 단계·목표 인덱스를 고른다. 재도전 뒤 앞 목표에서 종료하면 실제 마지막 위치와 달라질 수 있다. 이번 목표 표본의 `retry_count`는 모두 0이므로 **재도전 사례의 수치 오류는 이번 표본에서 실증하지 못했다**.
- 날짜는 Sessions는 `started_kst`, Events는 `occurred_at_kst`, 목표는 `received_kst`로 필터링한다. 지연 업로드나 자정 통과 시 같은 도전의 세 화면이 다른 대상을 고를 수 있다. `received_kst`는 플레이 발생 시각이 아니다.
- 수정: ‘최대 도달’과 ‘최근 기록/확인된 종료’를 나눈다. 목표 종료가 completed라는 이유만으로 튜토리얼 전체 완료·이탈을 단정하지 않는다. 기본 날짜 기준은 **도전 시작일 코호트**로 통일하고, 실제 사건 시각 범위가 필요하면 별도 모드로 표시한다.
- 목표 시각은 기존 `onboarding_step` Events의 발생 시각과 연결해 표시한다. 과거 자료에서 연결할 수 없으면 ‘업로드 시각’이라고 표시한다. 수신 시각을 발생 시각으로 이름만 바꾸지 않는다.
- 현재 온보딩은 설정 `onboarding-2026-10-17-stage-ids-5`의 **0-1~0-5**다. 과거 7단계와 초기 2구간 자료는 같은 단계 번호만으로 학습 목표를 합치지 않는다.

### F09 · P1 · 반응 시간을 성공 반응·동일 전조 기준처럼 해석할 위험 — 운영·코드 확인

- 위치: `renderCombat`, `CombatTelemetryRecorder.ResolveAttack`, `CombatTelemetrySignals.MarkReactionStart`, `HumanBossAttack.CounterDash`, `TwinHumanIai.Release`, `BeastBossAttack.TryShowPounceGlint`.
- 전체 표본의 반응 시간 1,640개에는 **피격(Hit)과 연결된 입력 107개**도 있다. 이 값은 성공적인 방어 시간만의 평균이 아니다. 입력과 접촉이 연결된 공격만 표본이므로 모든 공격에 대한 반응 능력도 아니다. 같은 입력이 여러 공격과 연결되면 공격별 표본이 된다.
- 현재 API는 `input_id`, `reaction_association`을 제외한다. `kind`는 이 사건에서 공격 종류이므로 방어/회피 입력 종류를 대신할 수 없다.
- 현행 코드의 특수 기준은 다음과 같다. 과거 빌드까지 같은 기준이었다고 단정할 수 없다.

| 패턴 | 현행 반응 기준 |
| --- | --- |
| 일반 수리검·일반 근접/Beast 공격 | 해당 공격의 Begin 전조 시점 |
| TwinHumanSlash | Warning이 시작되는 Begin 시점 |
| TwinHumanIai | 10초 차징 시작이 아닌 **Release의 암전 시작 직전 Begin** |
| TwinHumanCounterSlash | 제어자의 앞선 준비·밀어내기 전조가 아닌 **CounterDash 실제 실행 시작**. Begin과 Commit이 연이어 발생 |
| TwinBeastBite | 돌진 중 범위에 들어와 **PounceGlint 발생을 호출하는 순간**. 효과가 다 커진 뒤가 아님. 섬광이 발생하지 않으면 기존 Begin 기준이 남음 |

- 반격 베기 반응 표본은 전체 자료에서 **3개뿐이며 최대 약 0.062초**다. 이를 다른 패턴보다 반응이 우수하다고 해석하면 안 된다. 기준 시점과 표본 선택이 다르다.
- 시간은 `Time.realtimeSinceStartupAsDouble` 차이로 기록한다. 전조와 입력 사이에 일시정지가 끼면 그 시간이 포함될 수 있다. 일반 수리검에서 **45.764초** 표본을 확인했지만, 기존 자료만으로 이것이 일시정지 때문이라고 확정할 수는 없다.
- 사이트 수정: 입력 종류·결과·연결 근거·표본 수/커버리지와 기준 설명을 제공한다. 성공 결과와 피격 중 입력을 구분해 볼 수 있게 한다. 입력→접촉도 중복 제거한 resolved 공격만 대상으로 계산한다. 긴 값을 조용히 삭제하거나 0으로 보정하지 않는다.
- 추가 수집 제안: 향후 빌드에서 `reactionBasis`, 실제 기준 시각, 일시정지 제외 시계 또는 정지 포함 여부를 저장하고 설정 버전을 올린다. 이는 **별도의 Unity 작업·재빌드가 필요한 개선**이다. 이번 웹사이트 구현에서 과거 값을 재계산하거나 반격 전조를 임의로 앞당길 수 없다.
- 거합 역거합의 과거 Guard 오기록은 알려진 생산자 문제다. 새 코드 수정 이후의 PerfectParry는 그대로 집계한다. 기존 Guard 행 전체를 웹에서 PerfectParry로 일괄 변경하지 않는다.

### F10 · P1 · 퍼널의 단계 간 미도달 수가 실제 전환 집합과 다름 — 운영·코드 확인

- 위치: `renderStageFunnel`.
- 현재 ‘이전 지점 대비 미도달’은 단계별 독립 도달 수를 단순히 빼고 음수는 0으로 만든다. 체크포인트·이어 하기·날짜 범위가 있으면 앞 단계가 없는 뒤 단계 기록이 존재한다.
- 기본 표본에는 **2-1 없이 2-2가 기록된 run 1개**가 있다. 독립 집합 수의 차이는 이전 단계 진입자 중 다음 단계 미도달자 수와 같지 않다.
- 수정: `이전 단계에 도달한 run 집합 − 다음 단계에 도달한 run 집합`으로 계산한다. 뒤 단계 직접 진입은 별도로 표시한다. 기록된 진입 모드를 이용하고 없는 앞 단계를 만들어 채우지 않는다.
- 현재 중도 종료율의 ‘도전 기준’ 정의는 유지한다. `run_id`는 이어 하기로 재사용되고 PC 익명 ID는 사람 식별자가 아니므로 이를 참가자 영구 이탈률로 바꾸어 부르지 않는다.

### F11 · P1 · 보스전 평균 처치 0을 보스 미처치로 읽게 됨 — 운영·코드 확인

- 위치: `renderOverview`, `CombatTelemetryRecorder.HandleKill`(470행), 스테이지 제어자의 보스 완료 처리.
- `kills`는 Spawner의 **일반 적 처치**에만 더해진다. 전체 표본에서 1-2 클리어 23건, 2-2 클리어 27건이 모두 `kills=0`이다. 저장이 실패했다는 뜻이 아니다.
- 수정: 웨이브에는 ‘평균 일반 적 처치’, 보스전에는 ‘보스전 완료/완료율’과 가능한 개체 처치를 표시한다. 쌍둥이는 기존 Human/Beast defeated 값을 사용한다. 1막은 구간 완료를 근거로 파생한 완료 수임을 명시한다.
- 현재 평균 활성 플레이는 **구간 도전당 평균**이다. 5~10분 게임 목표 달성 여부를 이 값 하나로 판단하면 안 된다. 추가 분석이 필요하면 run별 활성 시간 합을 완료 실행과 미완료 실행으로 나누고, 이어 하기와 선택 빌드·기간의 포함 범위를 표시한다.

### F12 · P2 · 여러 전장의 히트맵을 한 대나무 맵처럼 표시할 수 있음 — 코드 확인

- 위치: `heatData`(1041행), `drawHeatmap`(1089행), CSV `localRowsInScope`.
- 다중 선택은 각 Arena 중심을 맞춰 셀을 합친다. 서로 다른 맵을 함께 고르면 다른 지형의 좌표가 겹치며, 선택에 1막이 하나라도 있으면 2막 표본에도 같은 대나무 오버레이가 깔린다.
- 수정 권장: 상단 구간 다중 선택은 유지하고 히트맵은 Arena/맵 그룹별로 나눠 보게 한다. 같은 맵인 1-1/1-2 등은 명시적으로 합산할 수 있다. 선택 전체를 겹칠 경우 ‘서로 다른 전장 중심을 맞춘 합성도’라고 표시하고 특정 맵 벽을 덮지 않는다.
- Events의 `stage_config`가 없는 과거 자료는 중심을 0으로 가정했다는 점을 표시한다. 설정이 없는데 실제 중심을 확인했다고 표시하지 않는다.
- 필터 메타데이터가 없는 보조 CSV는 Sessions 연결이 없으면 빌드·Editor 필터 적용을 확정할 수 없다. 해당 카드에 제약을 표시한다. 지금처럼 필터를 조용히 무시하지 않는다.

### F13 · P2 · 데이터 품질·버전 표시와 로컬 소스의 낙후 — 운영·코드 확인

- 위치: `renderQuality`, `patternLabels`, 문서와 배포 소스.
- 정상적인 `DefenseShuriken`이 라벨 목록에 없어 미등록 패턴 경고 대상이 된다. 한글 라벨과 알려진 과거 식별자를 보완한다. 알 수 없는 패턴은 계속 원래 ID를 보인다.
- 현재 품질 화면은 원본 행 수·몇 가지 필드만 확인한다. 중복 키, 고아 도전, Events/Sessions 불일치, 미분류 outcome, 목표 메타데이터 결합 누락, 오래된 데이터 여부가 드러나지 않는다.
- 최초 연결·버튼 새로고침 시 조회하며 지속적인 자동 폴링은 없다. 자동 연결이라는 표현이 실시간 무제한 동기화를 뜻하지 않도록 최종 조회 시각을 표시한다. 전체 5만 행 조회를 짧은 간격으로 겹쳐 실행하지 않는다.
- 배포 v12와 Unity 저장소의 사이트 복사본·기능명세가 불일치한다. 배포 완료 후 소스·생성 Worker·문서가 어느 버전인지 함께 갱신해야 한다.

## 3. 구현 전 확정할 집계 계약 — 권장안

| 지표 | 권장 단위·분모 |
| --- | --- |
| 구간 도전 | 최신 요약으로 중복 제거한 `stage_attempt_id` 수 |
| 사망 합계/평균 | 해당 도전의 deaths 합계 / 기록된 deaths 값이 있는 도전 수. 사람당 사망 수와 구별 |
| 도전 중 사망 비율 | 사망 도전 / 선택한 전체 도전. 진행 중 포함 수를 함께 표시하고 임의로 분모를 바꾸지 않음 |
| 일반 적 처치 | 웨이브 도전의 kills. 보스 처치와 별도 |
| 적 공격 실행 | session_id+attack_id별 Commit 한 번. 발사체는 각 수리검별 한 번 |
| 유효 공격 판정/적중률 | Commit된 공격 중 Cancelled·Interrupted를 제외한 최초 최종 결과. Hit / 유효 판정. Destroyed·Invulnerable 등 포함 여부를 결과 표에서 설명 |
| 피해량 비중 | 패턴별 실제 적용 피해 합 / 전체 실제 적용 피해 합 |
| 피격 횟수 비중 | 해당 패턴의 양수 피해 접촉 수 / 전체 양수 피해 접촉 수 |
| 방어 입력/접촉 | 고유 input_id의 입력 수와 고유 공격 접촉 수를 별도 표시. 한 방어 입력이 여러 공격을 막을 수 있음 |
| 반응 시간 | 같은 기준·입력 종류·결과·수집 버전의 연결 표본. 공격 접촉별 평균·중앙값·표본 수·연결 비율 제공 |
| 온보딩 목표 완료율 | 목표 종료 행 중 completed 비율. 튜토리얼 전체 완료 실행 비율과 구별 |
| 중도 종료율 | 현행 ‘확인된 중도 종료 도전 / 완료·사망·종료가 확정된 도전’ 유지. 미확정 별도 |
| 저장 진행 퍼널 | run 집합의 실제 포함·차집합. 같은 run의 이어 하기 포함, 사람 수를 뜻하지 않음 |
| 기본 날짜 | 도전 시작일 코호트. 사건 시각 분석은 별도 모드로 표시 |
| 누락 | 0과 구분하고 집계 가능 표본 수·부족한 출처를 표시 |

공통 키 규칙: 사건은 `event_key` 또는 session_id+event_sequence, 도전은 stage_attempt_id, 공격은 session_id+attack_id다. 공격 ID가 없거나 0인 과거 행 전체를 하나로 합치지 않는다. 목표는 가능한 기존 step_key를 사용하고 Sessions 메타데이터를 연결한다. 정규화는 브라우저 내부 분석 데이터에만 적용하며 원본 행은 보존한다.

## 5. 구현 범위와 배포 영향

| 범위 | 필요 여부 |
| --- | --- |
| 사이트 HTML/JS·Worker 수정 및 Sites 배포 | 필요 |
| Apps Script 읽기 허용 열·스냅샷 조회 계약 수정 | 필요. 로컬 Code.gs에 반영 완료 |
| Apps Script 기존 웹 앱 새 버전 배포 | 사용자 저장·배포 완료. 이후 사이트 서버 리다이렉트 수정은 Apps Script 재배포 없이 적용했다 |
| 기존 시트 데이터 삭제·과거 행 수정 | 필요 없음 |
| 기존 빌드의 로그 업로드 주소·토큰·설정 교체 | 필요 없음 |
| 반응 시계·기준 등 새 정보의 Unity 수집 | 별도 후속 작업으로만 진행. 적용 시 새 빌드·수집 설정 버전 구분 필요 |

전체 payload_json을 브라우저로 보내는 방법을 기본 해결책으로 삼지 않는다. 기존 구조화 열·최신 Sessions의 필요한 패턴 요약을 사용하고 응답 크기를 측정한다. 이 검토에서 확인한 502와 수분 단위 전체 조회를 고려해 불필요한 전체 재조회·중복 전송을 늘리지 않는다.

## 6. 운영 반영 순서

1. `tools/combat_telemetry/google_apps_script/Code.gs`를 Apps Script 편집기에 반영해 저장한다.
2. 배포 관리에서 현재 웹 앱 배포를 수정하고 새 버전을 배포한다. 기존 `/exec` URL, 실행 사용자, 액세스 권한, Script Properties를 유지한다.
3. Sites v15와 Apps Script 스냅샷 계약은 배포됐다. 새로 열린 대시보드는 자동으로 조회하고 진행 행 수를 표시한다. 이미 열린 이전 버전 화면은 페이지를 새로고침한다. 현재 서버 리다이렉트 수정만 적용할 때는 Apps Script 추가 배포가 필요 없다.

- 2026-10-19 추가 확인: 사용자가 스냅샷 계약을 Apps Script에 저장·배포했다. 운영 `dataset=core` 응답은 HTTP 200, Events 행 상한 58,013, Sessions 344행, OnboardingSteps 208행이었다. generation 0 / rowLimit 58,013을 명시한 Events 1행 요청도 HTTP 200으로 같은 스냅샷을 반환했다. 스냅샷을 지정하지 않은 10행 페이지도 응답했지만 100행과 1,000행 요청은 `upstream_unavailable` 502로 실패했고, 전체 Events 수신은 완료되지 않았다. 독립 Events 조회의 전체 행 수가 58,013에서 58,029로 늘어난 점도 확인했다. 로컬 `dashboardRowsPage`를 `getDisplayValues()`에서 `getValues()`로 바꾸고 Date 값은 KST 문자열로 정규화해 표시 형식을 보존하도록 수정했다. 해당 변경은 JavaScript 문법 검사를 통과했으며, 사용자가 Apps Script에 저장·새 버전 배포한 뒤 페이지 크기와 전체 새로고침을 다시 확인해야 한다.
